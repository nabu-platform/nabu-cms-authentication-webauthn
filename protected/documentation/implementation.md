# Current source state

## Challenge integration investigation (17 November 2026)

No additional-factor provider was enabled. `nabu.cms.core.v2.security.web.login` selects weighted `category=challenge` types and discovers `challengeHandler` implementations by `challengeType`; it invokes the handler with `userId` before creating a five-minute `challenge` temporary authentication. Completion must consume that exact pending authentication, validate an assertion tied to its identity, application and security context, and return via the core login flow. The indexed challenge handler input still exposes only `implementationId` and `useAsContext`; an attempted addition of `userId` reported success without changing indexed readback. An attempted Blox creation reported success, but its fragments remained invisible to the indexed reader and it was removed. The indexed verifier still exposes nested `request` despite Java source accepting flat parameters; malformed nonmutating invocation fails before verification. Mapping flat verifier fields failed artifact validation, so the existing finish and primary authenticator guards were preserved. Do not configure `webauthnChallenge` as an active challenge until repository persistence, verifier indexing and the pending-token completion contract are repaired and tested. Primary `webauthn` remains separate from TOTP; document approval/signature purposes are suspended.


## Active runtime state (16 November 2026)

The Java index now exposes `WebAuthnRequest.publicKeyFormat` and `WebAuthnResult.valid`, `reason`, `algorithm`, `publicKeyFormat`. Both Blox finish services reject null/false `verified/valid` immediately after verifier output, before success metadata processing or the transaction that consumes the ceremony and inserts/updates credentials. Assertion supplies trusted literal SPKI for the `publicKeySpki` database column, permits stored -7 or -257, and registration requires verified SPKI and maps ES256 to -7 and RS256 to -257. The atomic consume and update/create paths remain unchanged. The source also contains unconditional WebAuthn-only entry rejection in both finish services and `providers.authenticate`: a safe invocation of `nabu.utils.WebAuthn.verifyRegistration` with malformed response fails before the verifier body in `TypeUtils.getAsBean` / `MethodServiceInstance.execute` with `IllegalArgumentException: nabu.utils.types.WebAuthnRequest is not an interface`. Fix runtime POJO request binding and demonstrate safe invalid and valid verifier outcomes before removing those three guards. Public registration REST wrappers already reject at entry; unrelated CMS password login is unchanged. The `specs.verify*` artifacts are dispatch-only, not wired implementations, and their fragment manager retains legacy output fields despite successful edit responses; do not use them for authentication. No live finish service, database mutation, schema update, deployment, or restart was performed.

## Superseded November 2026 verifier integration blocker

Java source `eai-module-utils/WEBAUTHN-CONTRACT.md`, `WebAuthnRequest`, `WebAuthnResult`, and `WebAuthn` now implement verdict-based ES256/RS256 registration and assertion with mandatory assertion publicKeyFormat. The runtime jar is not deployed. The indexed `nabu.utils.types.WebAuthnRequest` lacks `publicKeyFormat` and `nabu.utils.types.WebAuthnResult` lacks `valid`, `reason`, `algorithm`, `publicKeyFormat`. Blox rejects references to these fields during fragment validation. Consequently the CURRENT `services.finishRegistration` and `services.finishAssertion` still do not check `valid`, registration still stores hardcoded -7, and assertion still requires -7 and omits publicKeyFormat. Do not enable registration or WebAuthn login until the Java library is loaded/reindexed and both finish services are rewired and validated. Existing credential keys are SPKI; pass the server-side literal SPKI for them, without a schema migration. The two `specs.verify*` outputs now include Java verdict and success metadata, but the serviceInterface fragment manager retained legacy `verified` (and registration `publicKeySpki`) fields when editing; these specs must be cleaned up and their dispatch-only indexed inputs repaired before use. They are not executable verifiers. See `integration.md` for the browser contract. No deployment, schema or live DB change has been performed.

## Models and configuration

- `types.credential`: persist against the canonical CMS owner UUID, with exact RP ID and canonical unpadded base64url credential ID. Add a **database unique composite constraint `(rp_id, credential_id)`** before any writes. Store verified P-256/ES256 public key as SPKI, opaque randomly assigned userHandle, signCount, backup flags, timestamps and revocation. Reject duplicate IDs even if registered under another owner; never reassign ownership.
- `types.ceremony`: one-use, short-lived random challenge with purpose (`assertion` or `registration`), RP ID, exact origin, server-owned context, canonical owner, realm and requested alias. Atomic consume must require `consumed IS NULL AND expires > now`, under row lock or conditional update in the same transaction as credential insert or counter update. Never accept a caller-provided ceremony as authority.
- `configuration.policy`: explicit RP ID and exact HTTPS origin allowlist, bounded timeout and required user verification. Missing, empty, inconsistent or insecure configuration must disable options and finish endpoints; do not infer policy from request headers.

## Validated scaffolding and immediate blocker

The five artifacts `types.credential`, `types.ceremony`, `configuration.policy`, `specs.verifyAssertion` and `specs.verifyRegistration` exist. Both verifier `output.xml` fragments are visible on readback, but **both `input.xml` fragments still read as only optional `implementationId` and `useAsContext`**. Attempts to edit each input through the editable serviceInterface fragment manager returned success, yet immediate indexed readback still returned the defaults. Whether this is failed persistence or a stale fragment index is unconfirmed; until independently verified neither verifier has a usable input contract; do not implement a caller against these inputs. The serviceInterface manager loads/saves `pipeline.xml`; diagnose its fragment update and reindex/reload path, then write and independently read back inputs for assertion (policy, server-loaded ceremony, stored credential, untrusted response JSON) and registration (policy, server-loaded ceremony, untrusted response JSON). Require these fields and never trust a browser-supplied ceremony, credential, policy or owner. `implementationId` and `useAsContext` are dispatch fields supplied by the service-interface wrapper, not WebAuthn proof.

No WebAuthn/FIDO2 verifier dependency or Java implementation was found in the checked Java sources and POMs (`main`); those Maven modules compile for Java 8 (`source` 1.8). Select a maintained, audited library with an explicitly Java 8-compatible version and inspect its transitive dependencies and license before adding it. Java `parsePublicKey` and `verifySignature` helpers were reported locally built/tested but are not deployed and do not parse or validate a WebAuthn ceremony. Library selection and deployment are prerequisites for trustworthy verification, not an external-party blocker; integration work remains outstanding.

A synchronizable dataModel was deliberately not added: the existing credential structure marks `credentialId` indexed but does not establish uniqueness of `(rp_id, credential_id)`. Before synchronizing, provide a reviewed, non-destructive migration for the target database dialect that adds that composite unique constraint, then include both existing structures in a database model; do not execute schema synchronization as part of scaffolding.

## Missing full verifier contract

Implement `specs.verifyAssertion` and `specs.verifyRegistration` using a maintained, audited WebAuthn/FIDO2 library with strict CBOR/COSE and authenticator-data parsing; do not implement ad hoc CBOR. Reject malformed, noncanonical or oversized base64url/JSON/CBOR and duplicate JSON keys; decode `clientDataJSON` bytes and verify exact `type`, challenge and origin (plus crossOrigin/topOrigin policy). Verify raw authenticatorData RP ID SHA-256, UP and UV, reserved bits and backup flag invariants; enforce ES256 (-7), EC2 P-256 key validity, and signed bytes `authenticatorData || SHA-256(clientDataJSON)` with the stored SPKI. Assertion must match raw ID, ceremony owner and RP, optional userHandle against stored opaque handle, allowed credential list and revocation. Compare signCount against stored counter according to WebAuthn clone-detection rules (zero counters allowed only under explicit risk policy; nonzero regression rejects), and atomically update counter/backup flags with ceremony consumption. Registration additionally validates attestationObject format and trust policy, attested credential data and exact returned credential ID, algorithm/key and exclusion list. Generate userHandle and challenge on the server with a CSPRNG; never use account alias/UUID as userHandle.
