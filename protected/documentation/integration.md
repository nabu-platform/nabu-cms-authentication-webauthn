# Custom WebAuthn integration

All IDs below are prefixed `nabu.cms.authentication.webauthn.`. These are server-side services, not publicly callable endpoints. Resolve `applicationId` from the current web application, `origin` from the actual HTTPS request and the enrollment identity from the authenticated server security context. Do not map client-supplied application, owner, realm, authorization flag, or origin directly to a service call. The current implementation uses `nabu.cms.core.services.user.getCurrent` to select the enrollment identity; custom pending signup MUST establish an authenticated, non-anonymous identity in that context for BOTH calls. A mere signup form, email address, or client-provided user ID is not authority to enroll. The identity ID, alias, realm and canonical owner must remain the same at finish; the persisted ceremony stores identity, owner, realm, alias, RP, origin and application context. Verify the finish service checks `enrollmentIdentityId` before enabling any registration wrapper. Authorize pending signup ownership in the wrapper before exposing either step. No anonymous enrollment primitive is provided.

## Registration

`services.registrationOptions` input: `{applicationId: string, origin: string, password?: string, requireActiveAccount?: boolean}`. Output: `{ceremonyId: UUID, challenge: base64url, rpId: string, userHandle: base64url, excludedCredentials: string[], expires: date, timeout: milliseconds}`. `services.finishRegistration` input: `{applicationId, origin, ceremonyId: UUID, responseJson: string, password?: string, requireActiveAccount?: boolean}`; output `{credentialId: string}`. This is source wiring, not a verified deployed capability. Both finish services and the typed WebAuthn authenticator currently reject all calls at entry because a nonmutating runtime invocation of `nabu.utils.WebAuthn.verifyRegistration` fails before verification with `IllegalArgumentException: nabu.utils.types.WebAuthnRequest is not an interface` in `TypeUtils.getAsBean` / `MethodServiceInstance.execute`. Resolve Java request object binding and retest the verifier before removing these guards. The indexed finish service binds enrollmentIdentityId and conditions active-account checks on requireActiveAccount; verify the deployed behavior before enabling pending enrollment. Omitted password must be allowed ONLY for a trusted wrapper which independently authorized the current enrollment identity; supplied passwords must validate even for pending users. The existing public `api.rest.registrationOptions` and `api.rest.finishRegistration` wrappers are temporarily fail-closed at runtime; do not expose them until their server-side `requireActiveAccount=true` and password guards, enrollment binding and contract are independently verified. Neither accepts a client-provided disable flag. After the finish utility has been repaired and verified, a custom pending signup wrapper may omit password and leave `requireActiveAccount` unset after server-side signup authorization; this does not relax login eligibility. Never expose these services directly to arbitrary clients or forward a client boolean to `requireActiveAccount`. The wrapper must maintain the authenticated enrollment identity across both requests (for example with its own server-managed signup session); do not treat ceremonyId as authorization.

Build `navigator.credentials.create({publicKey})` using `challenge=decodeBase64url(output.challenge)`, `rp={id: output.rpId, name: applicationDisplayName}`, `user={id: decodeBase64url(output.userHandle), name: currentIdentity.alias, displayName: accountDisplayName}`, `pubKeyCredParams=[{type:'public-key',alg:-7},{type:'public-key',alg:-257}]` (ES256 and RS256 only), `excludeCredentials=output.excludedCredentials.map(id => ({type:'public-key',id:decodeBase64url(id)}))`, `timeout=output.timeout`, `attestation='none'`, and `authenticatorSelection.userVerification` from `utils.getPolicy` for the same trusted application (`required` if true, otherwise `preferred`). Serialize the returned PublicKeyCredential with base64url `rawId`, `response.clientDataJSON`, `response.attestationObject` and `response.getTransports()` as appropriate for the deployed Java verifier; send this JSON string as `responseJson` along with the server-issued `ceremonyId` to finish. The server verifier, not the browser options, decides validity. Java `verifyRegistration` returns `result.valid`; only `valid=true` supplies credentialId, unpadded base64url SPKI publicKey, publicKeyFormat=`SPKI`, algorithm=`ES256` or `RS256`, signCount and backup flags. The finish service must reject `valid != true` before consuming a ceremony or inserting a credential; persist algorithm as -7 or -257 and the SPKI key. `valid=false` supplies reason `INVALID_RESPONSE` or `VERIFICATION_FAILED` and no verified metadata. Server policy errors and unexpected dependency/provider failures throw rather than returning a verdict. Finishing stores a credential but never activates/verifies the account or creates a CMS login session; the signup wrapper remains responsible for email verification, account activation, recovery setup and its own session lifecycle.

## Login and recovery

Call `services.authenticationOptions` with `{alias, realm, applicationId, origin}` using a server-derived application realm; output is `{ceremonyId, challenge, rpId, allowedCredentials, expires, timeout}`. For browser `navigator.credentials.get({publicKey})` use `challenge=decodeBase64url(challenge)`, `rpId`, `allowCredentials=allowedCredentials.map(id => ({type:'public-key',id:decodeBase64url(id)}))`, `timeout`, and `userVerification` resolved from the same effective policy. Encode the assertion credential response as JSON with base64url `rawId`, `response.authenticatorData`, `response.clientDataJSON`, `response.signature`, and optional `response.userHandle`. Invoke the existing CMS `POST /security/user/login` with `{authenticationId: alias, type:'webauthn', secret: JSON.stringify({ceremonyId, credentialId: rawId, responseJson: JSON.stringify(assertionCredential)})}`. The registered `providers.authenticate` uses strict `nabu.utils.WebAuthn.parseAssertionEnvelope` and `services.finishAssertion`; malformed envelopes throw and must fail login, not downgrade authentication. `verifyAssertion` separately returns `result.valid=false` with `INVALID_RESPONSE`, `VERIFICATION_FAILED`, or `INVALID_STORED_KEY`; only `valid=true` authorizes ceremony consumption, counter/backup update, and identity authentication. Supply required `request.publicKeyFormat=SPKI` from trusted server storage for existing and new credentials, never browser JSON. Java also accepts COSE only if the credential's trusted persisted format is COSE; the current Nabu credential column stores SPKI, so existing rows need no migration or re-enrollment. The assertion result reports validated key algorithm and format, not a new public key. Unexpected errors throw fail closed.  typed authentication, active-account/realm checks, `canLoginAs` and the existing CMS bearer/session issuance remain in that login path. Do not create a token directly from registration or assertion results. Inactive, blocked and unverified accounts cannot log in. Keep an independent recovery factor (password or a reviewed account recovery flow) so users can recover after loss of every passkey.

`services.listCredentials` input `{applicationId, origin}` returns `{credentials: types.credentialSummary[]}` for the current verified identity and RP. `services.revokeCredential` input `{applicationId, origin, credentialId: UUID}` returns `{success: boolean}` and conditionally revokes only a credential of the current verified owner and RP. Use the existing protected REST `GET /security/webauthn/credentials` and `DELETE /security/webauthn/credentials/{credentialId}` where suitable. Do not expose internal CRUD lists (they include verifier keys/handles), or atomic JDBC services.

## Independent additional factor (blocked; not enabled)

Passkey authentication via `providers.authenticate` and `services.finishAssertion` is a typed login path; it does not satisfy or replace TOTP. The application selects separate, unrelated authentication capabilities. For a standalone WebAuthn challenge factor, register a distinct `challenge` authentication type in the application's weighted authentication selection and provide an implementation of `nabu.cms.core.v2.specs.challengeHandler` discoverable by `nabu.cms.core.v2.security.web.login` under the implementation property `challengeType` equal to that type's name. The login flow calls the matching handler with the authenticated token's `authenticationId` as `userId`, then issues a temporary authentication of type `challenge`; the selected type is not automatically completed by a passkey login. The current indexed `challengeHandler` input exposes only `implementationId`/`useAsContext` and its output is empty, while the login service links `userId` to the invocation; verify the effective service-interface pipeline contract before implementing. The application must specify the challenge initiation/completion endpoints, temporary-authentication binding, server-owned application/origin/context, and which step verifies the independent assertion and advances the challenge. No provider or automatic TOTP bypass is implemented here. On 17 November 2026, `nabu.utils.WebAuthn.verifyAssertion` still exposes a nested `request` input, while the current Java source uses flat parameters. A nonmutating malformed assertion invocation fails with `WebAuthnRequest is not an interface` before verification. The finish service remains guarded, and attempted flat field mappings fail repository validation against the indexed contract. The repository fragment writer also reports success for changes that do not appear in indexed readback; a newly created Blox artifact was not visible to the indexed reader and was removed. A safe completion provider cannot be enabled until the verifier service is loaded with its flat contract, artifact persistence/readback works, and the challenge handler contract is extended to carry server-owned application, origin and the issued temporary authentication binding. Never accept an assertion from the primary typed `webauthn` provider as completion of a different pending challenge. No WebAuthn-specific public error codes are whitelisted; internal nonwhitelisted codes may still aid diagnostics.

## Deployment and checks

`utils.getPolicy` derives HTTPS RP/origins from the application without a required policy document; optional application `configuration.policy` or system properties override defaults. Default timeout is 120 seconds and UV is true; explicit configured false is respected. See `policy.md` for exact precedence and outstanding ambiguity limitation. Before enabling, repair the active Java verifier request binding, verify its results with nonmutating tests, then remove the temporary fail-closed WebAuthn-only entry guards together with the project; review `migration.md`; have the application install `database.model` including `enrollment_identity_id` on ceremonies and enforce unique `(rp_id, credential_id)` on credentials before writes. Verify CRUD internal permissions/context-to-owner create behavior with the deployed provider. No live schema changes were performed. Runtime calls confirmed both public registration wrappers reject supplied passwords with `Registration temporarily unavailable pending verified enrollment binding`. Indexed fragment readback did not reflect successful edits and the finish utility could not be independently validated; full HTTPS integration tests require an application, deployed database schema and authenticated enrollment identities. Run HTTPS end-to-end tests for pending signup continuity, public REST password enforcement, invalid supplied passwords, replay/concurrent finish, cross-context/owner/origin/RP, malformed and duplicate-key JSON, UV false/true, blocked/unverified login, revocation and recovery before deploying.
