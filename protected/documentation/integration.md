# Custom WebAuthn integration

All IDs below are prefixed `nabu.cms.authentication.webauthn.`. These are server-side services, not publicly callable endpoints. Resolve `applicationId` from the current web application, `origin` from the actual HTTPS request and the enrollment identity from the authenticated server security context. Do not map client-supplied application, owner, realm, authorization flag, or origin directly to a service call. The current implementation uses `nabu.cms.core.services.user.getCurrent` to select the enrollment identity; custom pending signup MUST establish an authenticated, non-anonymous identity in that context for BOTH calls. A mere signup form, email address, or client-provided user ID is not authority to enroll. The identity ID, alias, realm and canonical owner must remain the same at finish; the persisted ceremony stores identity, owner, realm, alias, RP, origin and application context. Verify the finish service checks `enrollmentIdentityId` before enabling any registration wrapper. Authorize pending signup ownership in the wrapper before exposing either step. No anonymous enrollment primitive is provided.

## Registration

`services.registrationOptions` input: `{applicationId: string, origin: string, password?: string, requireActiveAccount?: boolean}`. Output: `{ceremonyId: UUID, challenge: base64url, rpId: string, userHandle: base64url, excludedCredentials: string[], expires: date, timeout: milliseconds}`. `services.finishRegistration` input: `{applicationId, origin, ceremonyId: UUID, responseJson: string, password?: string, requireActiveAccount?: boolean}`; output `{credentialId: string}`. This is the intended contract, not a verified deployed capability: the indexed finish service still shows a mandatory password, unconditional active-account checks, and no enrollment-identity comparison. Do not use passwordless pending enrollment until the actual source is verified and corrected. Omitted password must be allowed ONLY for a trusted wrapper which independently authorized the current enrollment identity; supplied passwords must validate even for pending users. The existing public `api.rest.registrationOptions` and `api.rest.finishRegistration` wrappers are temporarily fail-closed at runtime; do not expose them until their server-side `requireActiveAccount=true` and password guards, enrollment binding and contract are independently verified. Neither accepts a client-provided disable flag. After the finish utility has been repaired and verified, a custom pending signup wrapper may omit password and leave `requireActiveAccount` unset after server-side signup authorization; this does not relax login eligibility. Never expose these services directly to arbitrary clients or forward a client boolean to `requireActiveAccount`. The wrapper must maintain the authenticated enrollment identity across both requests (for example with its own server-managed signup session); do not treat ceremonyId as authorization.

Build `navigator.credentials.create({publicKey})` using `challenge=decodeBase64url(output.challenge)`, `rp={id: output.rpId, name: applicationDisplayName}`, `user={id: decodeBase64url(output.userHandle), name: currentIdentity.alias, displayName: accountDisplayName}`, `pubKeyCredParams=[{type:'public-key',alg:-7}]`, `excludeCredentials=output.excludedCredentials.map(id => ({type:'public-key',id:decodeBase64url(id)}))`, `timeout=output.timeout`, `attestation='none'`, and `authenticatorSelection.userVerification` from `utils.getPolicy` for the same trusted application (`required` if true, otherwise `preferred`). Serialize the returned PublicKeyCredential with base64url `rawId`, `response.clientDataJSON`, `response.attestationObject` and `response.getTransports()` as appropriate for the deployed Java verifier; send this JSON string as `responseJson` along with the server-issued `ceremonyId` to finish. The server verifier, not the browser options, decides validity. Finishing stores a credential but never activates/verifies the account or creates a CMS login session; the signup wrapper remains responsible for email verification, account activation, recovery setup and its own session lifecycle.

## Login and recovery

Call `services.authenticationOptions` with `{alias, realm, applicationId, origin}` using a server-derived application realm; output is `{ceremonyId, challenge, rpId, allowedCredentials, expires, timeout}`. For browser `navigator.credentials.get({publicKey})` use `challenge=decodeBase64url(challenge)`, `rpId`, `allowCredentials=allowedCredentials.map(id => ({type:'public-key',id:decodeBase64url(id)}))`, `timeout`, and `userVerification` resolved from the same effective policy. Encode the assertion credential response as JSON with base64url `rawId`, `response.authenticatorData`, `response.clientDataJSON`, `response.signature`, and optional `response.userHandle`. Invoke the existing CMS `POST /security/user/login` with `{authenticationId: alias, type:'webauthn', secret: JSON.stringify({ceremonyId, credentialId: rawId, responseJson: JSON.stringify(assertionCredential)})}`. The registered `providers.authenticate` uses strict `nabu.utils.WebAuthn.parseAssertionEnvelope` and `services.finishAssertion`; typed authentication, active-account/realm checks, `canLoginAs` and the existing CMS bearer/session issuance remain in that login path. Do not create a token directly from registration or assertion results. Inactive, blocked and unverified accounts cannot log in. Keep an independent recovery factor (password or a reviewed account recovery flow) so users can recover after loss of every passkey.

`services.listCredentials` input `{applicationId, origin}` returns `{credentials: types.credentialSummary[]}` for the current verified identity and RP. `services.revokeCredential` input `{applicationId, origin, credentialId: UUID}` returns `{success: boolean}` and conditionally revokes only a credential of the current verified owner and RP. Use the existing protected REST `GET /security/webauthn/credentials` and `DELETE /security/webauthn/credentials/{credentialId}` where suitable. Do not expose internal CRUD lists (they include verifier keys/handles), or atomic JDBC services.

## Deployment and checks

`utils.getPolicy` derives HTTPS RP/origins from the application without a required policy document; optional application `configuration.policy` or system properties override defaults. Default timeout is 120 seconds and UV is true; explicit configured false is respected. See `policy.md` for exact precedence and outstanding ambiguity limitation. Before enabling, deploy the indexed Java verifier/parser together with the project, review `migration.md`, synchronize `database.model` including `enrollment_identity_id` on ceremonies and enforce unique `(rp_id, credential_id)` on credentials. Verify CRUD internal permissions/context-to-owner create behavior with the deployed provider. No live schema changes were performed. Runtime calls confirmed both public registration wrappers reject supplied passwords with `Registration temporarily unavailable pending verified enrollment binding`. Indexed fragment readback did not reflect successful edits and the finish utility could not be independently validated; full HTTPS integration tests require an application, deployed database schema and authenticated enrollment identities. Run HTTPS end-to-end tests for pending signup continuity, public REST password enforcement, invalid supplied passwords, replay/concurrent finish, cross-context/owner/origin/RP, malformed and duplicate-key JSON, UV false/true, blocked/unverified login, revocation and recovery before deploying.
